## 1. 阻塞问题（必须解决才能开始执行）

### 🔴 BLOCKER-1: 分页索引冲突（P0）

**位置**: Phase 1 - Task 1.2, Task 1.3, Task 1.4

**问题**: Spec 定义 `currentPage` 从 **0** 开始，但现有代码 `src/app/(admin)/admin/articles/page.tsx:53` 使用 **1-based** 分页（`current=${page}` 从 1 开始）。

**影响**: 所有列表页分页错误，用户永远看不到第一页数据。

**必须行动**:
1. 立即与后端确认分页索引策略（0-based vs 1-based）
2. 统一前后端分页契约
3. 更新所有 Task Spec 中的分页描述

**阻塞解除标准**: 后端确认分页索引，DataTable 接口契约更新

---

### 🔴 BLOCKER-2: 图片上传 API 未确认（P0）

**位置**: Phase 2 - Task 2.2, Task 2.3 / Phase 4 - Task 4.4

**问题**: Phase 2 和 Phase 4 都假设存在 `POST /api/v1/admin/upload` 接口，但现有项目中**未找到该 API 定义**。

**影响**: 
- 编辑器图片上传功能无法实现
- 封面图上传功能无法实现
- 相册拖拽上传功能无法实现

**必须行动**:
1. 立即与后端确认上传 API 是否存在
2. 确认 API 返回格式（是否匹配 `{code, flag, message, data: {url}}`）
3. 确认是否支持批量上传

**阻塞解除标准**: 后端提供上传 API 文档，或确定替代方案（Base64/外部图床）

---

### 🔴 BLOCKER-3: Dashboard 聚合 API 大概率不存在（P0）

**位置**: Phase 3 - Task 3.2, Phase 3 README

**问题**: Phase 3 需要 `recentActivities`、`topArticles`、`todoList`、`articleTrend` 等数据，但现有后端 API 仅返回基础统计（articleCount, userCount, messageCount, viewCount）。

**影响**: 
- Phase 3 核心功能（最近动态、热门文章、待办提醒）无法显示真实数据
- 若 API 不存在，Phase 3 工期需要从 5 天缩减为 2 天（仅统计卡片+趋势图）

**必须行动**:
1. 与后端确认 Dashboard 新字段是否能提供
2. 明确 API 交付时间
3. 制定降级方案（前端 mock/聚合计算）

**阻塞解除标准**: 后端确认 API 能力，或接受降级方案

---

### 🔴 BLOCKER-4: 关键依赖兼容性未验证（P0）

**位置**: Phase 4 - Task 4.3 (Lightbox)

**问题**: `yet-another-react-lightbox` peer dep 通常为 `^18.0.0`，在 React 19 下**可能安装失败或运行时异常**。

**影响**: 相册 Lightbox 预览功能可能无法使用，导致 Phase 4 核心功能受阻。

**必须行动**:
1. 执行 `npm install yet-another-react-lightbox --dry-run` 验证兼容性
2. 若失败，提前实施降级方案（自研 Lightbox 或 react-photo-album）

**阻塞解除标准**: 验证通过，或降级方案准备就绪

## 2. 优化建议（提高执行效率）

### 🟡 OPT-1: 任务拆分不合理

**问题**: 多个 Task 过大或过小

| Task | 当前工期 | 建议工期 | 理由 |
|------|---------|---------|------|
| TASK-1.2 DataTable 核心 | 1 天 | **2 天** | 涉及排序、筛选、搜索、批量选择、分页、骨架屏、空状态，功能点多 |
| TASK-1.4 其他列表页 | 1.5 天 | **3 天** | 7 个页面，平均每个页面不到 0.25 天，包括列定义、筛选器配置、API 对接 |
| TASK-2.2 图片上传 | 1.5 天 | **2 天** | 三种上传方式（拖拽/粘贴/点击）+ 批量 + 进度 + 错误处理 |
| TASK-3.2 Dashboard 布局 | 1 天 | **2 天** | 6 大模块 + 响应式 + API 降级处理 |
| TASK-4.2 瀑布流 | 1 天 | **1.5 天** | 响应式列数 + 懒加载 + 性能优化 |
| TASK-5.5 全局测试 | 1 天 | **1.5 天** | 7 种设备 × 10+ 页面 × 检查项，1 天过于紧张 |

**总工期调整**: 24 天 → **30-32 天**

---

### 🟡 OPT-2: 基础设施应提前到 Week 1

**问题**: EmptyState (Task 1.5) 和 Skeleton (Task 3.3) 分别放在 Phase 1 和 Phase 3，导致 Phase 1 列表页缺少空状态，Phase 2 编辑器缺少骨架屏。

**建议**: 
- **Week 1 前置**: 先完成 EmptyState + Skeleton + ErrorBoundary（2 天）
- 这些组件是全局基础设施，不依赖任何 Phase

---

### 🟡 OPT-3: Phase 3 部分任务可提前

**问题**: TASK-3.3 (Skeleton) 和 TASK-3.4 (EmptyState) 标注依赖 Phase 2，但实际上它们是独立的全局组件。

**建议**:
- TASK-3.3 和 TASK-3.4 可与 Phase 1 并行开发
- 完成后立即接入 Phase 1 的列表页，而非等到 Phase 3

---

### 🟡 OPT-4: 快捷键冲突未处理

**位置**: Phase 2 - Task 2.1

**问题**: `Ctrl+H` 在 Chrome 是"打开历史记录"，`Ctrl+S` 在部分编辑器中会触发浏览器保存。

**建议**:
- `Ctrl+H` → 改为 `Ctrl+Shift+H` 或 `Alt+H`
- `Ctrl+S` → 使用 `e.preventDefault()` 阻止浏览器默认行为
- 在工具栏显示快捷键提示（hover 时）

---

### 🟡 OPT-5: 批量删除缺少确认机制

**位置**: Phase 1 - Task 1.2 / Phase 4 - Task 4.4

**问题**: `BatchAction.onClick` 直接执行删除，无二次确认。

**建议**:
1. 批量操作必须显示 `Dialog` 二次确认
2. Destructive 操作显示红色警告 + 确认文字输入
3. 删除后显示 Toast + 撤销按钮（5 秒内可恢复）

## 3. 风险预警（可能导致延期）

### ⚠️ RISK-1: 后端 API 不满足需求（高概率，高影响）

**位置**: Phase 2, Phase 3, Phase 4

**具体风险**:
- Dashboard 聚合 API 不提供 → Phase 3 功能缩水
- 图片上传 API 不存在 → Phase 2 编辑器增强受阻
- 批量删除 API 不支持 → Phase 4 批量操作需循环调用

**缓解措施**:
1. **立即与后端对齐**（启动前必须完成）
2. 每个 Phase 开始前确认 API 就绪
3. 准备 mock 数据方案作为降级

**应急方案**:
- 若后端无法提供 Dashboard API → 仅保留统计卡片升级 + 趋势图
- 若后端无法提供上传 API → Phase 2 仅做工具栏，Phase 4 延后

---

### ⚠️ RISK-2: MDEditor 工具栏定制限制（中概率，高影响）

**位置**: Phase 2 - Task 2.1

**问题**: `@uiw/react-md-editor` 的 `commands` API 可能不支持完全自定义工具栏。

**影响**: Phase 2 核心功能（12 个按钮 + 快捷键）可能无法实现。

**缓解措施**:
1. 预研 MDEditor 的 `commands` API（启动前 0.5 天）
2. 如果无法定制，评估 Tiptap 迁移成本
3. 或者使用外部工具栏（独立于编辑器）+ ref 操作编辑器内容

---

### ⚠️ RISK-3: React 19 兼容性问题（中概率，中影响）

**位置**: 全项目

**问题**: 
- `yet-another-react-lightbox` 可能不兼容 React 19
- `recharts` 在 React 19 下可能有警告
- `framer-motion` 需验证兼容性

**缓解措施**:
1. 每个新增依赖安装后立即运行 `npm run build`
2. 保持依赖版本稳定，不随意升级
3. 准备降级方案（自研组件或替代库）

---

### ⚠️ RISK-4: 工期压缩导致测试不足（中概率，高影响）

**问题**: 原估算 24 天，建议调整为 30-32 天。若强行按 24 天执行，测试时间被压缩。

**影响**: 回归 bug 增加，质量下降。

**缓解措施**:
1. 严格按建议工期执行
2. 集成测试优先于单元测试（覆盖核心流程）
3. 每个 Phase 预留 0.5 天 buffer

---

### ⚠️ RISK-5: 移动端测试遗漏（中概率，中影响）

**位置**: Phase 5

**问题**: 
- 真机测试设备不足
- DevTools 模拟无法覆盖所有真机问题
- 第三方组件（MDEditor）移动端体验可能很差

**缓解措施**:
1. 使用 BrowserStack 或类似服务进行真机测试
2. MDEditor 移动端测试前置到 Phase 2
3. 准备编辑器只读降级方案

## 5. 验收标准质量审查

### ✅ 优点

1. **大部分验收标准可测试**: 使用了 checkbox 形式，部分有明确的测试方法（如 `npm run lint`、`npx tsc --noEmit`）
2. **BDD 场景覆盖**: 每个 Task 都有对应的 BDD Scenario，便于测试
3. **E2E 测试规划**: 每个验收标准都规划了 E2E 测试文件路径
4. **可追溯性矩阵**: SDD/BDD/TDD 三层可追溯，便于质量管理

### ⚠️ 问题

#### 5.1 缺少量化指标

| 模糊描述 | 建议改为 |
|---------|---------|
| "信息密度提升" | "列表页单屏展示行数从 10 行提升到 15 行" |
| "操作效率提升" | "筛选+排序+批量删除操作步骤从 6 步减少到 3 步" |
| "视觉体验提升" | "骨架屏加载时间 < 300ms，空状态有引导按钮" |
| "移动端可用" | "在 iPhone SE (375x667) 上可完成文章查看、编辑、删除" |

#### 5.2 部分验收标准主观

**问题示例**:
- "视觉体验提升" - 无法客观验证
- "动画流畅无卡顿" - "流畅"的定义不明确（FPS > 45？）
- "深色模式无视觉问题" - 需要具体检查清单

**建议**: 添加客观指标，如：
- 动画：FPS > 45（Chrome DevTools Performance 面板）
- 深色模式：所有文字对比度 ≥ 4.5:1（WCAG AA）
- 视觉：无布局偏移（CLS < 0.1）

#### 5.3 边缘情况遗漏

| Task | 遗漏的边缘情况 |
|------|---------------|
| TASK-1.2 | 大数据量（>1000 条）时表格性能 |
| TASK-1.2 | 网络中断时的错误处理 |
| TASK-2.2 | 上传过程中浏览器崩溃/关闭 |
| TASK-2.5 | localStorage 满时的处理 |
| TASK-3.2 | 所有 API 同时失败的降级 |
| TASK-4.2 | 图片加载失败时的占位 |
| TASK-4.3 | 大图（>10MB）加载性能 |
| TASK-5.5 | iOS Safari 底部安全区适配 |

#### 5.4 验收标准与 Spec 不一致

**发现**: 
- Task 1.2 接口定义中有 `ColumnDef<TData, any>[]`，但 Master Spec 要求避免 `any` 类型
- Task 2.1 快捷键 `Ctrl+Shift+C` 与 Chrome DevTools 冲突，但未在验收标准中验证冲突处理
